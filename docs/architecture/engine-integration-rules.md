# 新引擎接入与目录生成开发规则

本规则适用于 QLIE、YU-RIS 及以后新增的所有引擎，覆盖正式功能、测试脚本、实机验证和维护操作。
**新引擎只新增资源格式与运行方式的适配，必须复用公共任务、输出目录、启动入口和归档逻辑。**
不得因为接入或验证一个引擎，就在工作目录外层另建一套文件夹。

## 1. 统一目录结构

默认结构如下；用户选择其他文本保存目录时，仍按同样规则组织。

```text
工作目录/
├─ nagi/                                      程序代码
├─ translations/                              所选文本根目录
│  └─ 引擎族/游戏名-安装标识/
│     ├─ translation-任务编号/
│     │  ├─ 提取文本与必要的来源记录
│     │  ├─ partial-编号/                      本次部分翻译结果
│     │  ├─ full-编号/                         本次全文翻译结果
│     │  └─ workflow.json                      任务恢复记录
│     └─ character-glossaries/                 按公共规则保存的游戏级译名缓存
└─ playable/                                  与所选文本根目录同级
   ├─ 引擎族/游戏名-安装标识/
   │  ├─ 启动测试版.cmd                       指向测试版
   │  ├─ 启动正式版.cmd                       指向正式版
   │  ├─ translation-test/                    部分翻译；兼容旧 pilot
   │  │  ├─ game/                             独立游戏副本
   │  │  ├─ runtime/                          此副本所需的启动适配文件
   │  │  ├─ deployment.json                   部署清单
   │  │  └─ 启动汉化版.cmd                    版本内部入口
   │  └─ translation-formal/                  全文翻译，内部结构同测试版
   └─ .history/引擎族/游戏名-安装标识/         旧版及其存档
```

- 引擎族使用稳定名称，如 `QLIE`、`YU-RIS`；引擎版本、游戏版本和适配配置写入元数据，不另建版本级顶层目录。
- 游戏目录名使用公共 `game_folder()` 生成，保留安装路径标识，避免同名游戏或不同安装互相覆盖。
- 文本、API 返回和恢复记录按任务保存。可玩版按同一游戏的测试/正式两个固定位置保存，不随每次任务另建一套可玩目录。
- `playable` 必须是所选文本根目录的同级目录，不能硬编码为开发者的某个盘符或路径。
- 只在相应步骤需要时创建目录。只翻译部分内容时，不额外生成空的正式版目录或正式版入口。
- 不在 `translation-test`、`translation-formal` 内再次嵌套 `localized-game-编号`。
- 引擎可保留必要的脚本、语料、定位信息和回包记录；内部数据格式可以不同，但不能改变上述目录边界。

## 2. 必须复用的公共实现

| 职责 | 公共实现 | 新引擎的要求 |
| --- | --- | --- |
| 程序、数据和状态位置 | `nagi/paths.py` 中的 `application_root()`、`data_root()`、`state_root()`、`translation_root()` | 使用路径接口，兼容源码、安装包、便携版和旧数据；不从当前目录猜位置 |
| 引擎族和游戏安装标识 | `nagi/translation_storage.py` 中的 `engine_family()`、`game_folder()` | 注册新引擎族，复用标识规则 |
| 任务与可玩目录 | 同模块的 `workflow_root()`、`playable_root()`、`playable_slot()` | 由公共工作流生成，不在引擎适配器中拼接替代目录 |
| 目录安全检查 | 同模块的 `require_separate_output()` | 输出不得与原游戏重叠，也不得落入源码仓库 |
| 暂存、发布和旧版归档 | 同模块的 `deployment_paths()`、`publish_playable()` | 先校验完整暂存副本，再发布和归档 |
| 任务阶段与恢复 | `nagi/translation_workflow.py` | 接入提取、翻译、部署、断点与重启恢复，不另造一套任务管理 |
| 引擎部署分发 | `nagi/gameio/deployment.py` 的 `deploy_workflow()` | 按已识别的引擎和配置选择适配器 |
| 版本内启动器与游戏级入口 | `nagi/game_launcher.py` 的 `write_runtime_launcher()`、`publish_launcher()`、`validate_version_launcher()` | 复用运行时定位和测试/正式入口生成、校验逻辑 |

当前引擎识别、可玩路径白名单、工作流恢复和前端能力判断仍包含显式分支。
接入新引擎时必须同步检查这些位置，而不是只添加一个提取器或一个部署函数。
未知引擎应明确拒绝，不能落入 QLIE 或 YU-RIS 的默认分支。

README“功能边界”表是面向用户展示引擎游戏示例的固定位置。以后每新增一个游戏引擎，
必须在该表新增对应的“引擎游戏示例”行，列出有可核查来源的代表游戏，并在表后补充来源链接。
适配格式、版本限制和部署条件写入快速入门及参考文档，不以这些说明替代表中的游戏示例。

部署适配器接收公共工作流传入的任务和进度回调，在公共暂存目录中生成引擎资源，
完成校验和发布后返回版本内部的真实启动文件。游戏级测试/正式入口由公共工作流发布。
不得自行覆盖 `item.playable_root`，也不得把新任务的 `playable_layout_version` 改为旧版本来绕开目录规则。
旧目录分支仅用于兼容历史任务，不用于新引擎或新的验证脚本。

## 3. 三个步骤的文件边界

1. **提取**：只读原游戏，记录实际生效的资源层、来源身份、顺序、哈希和回填位置；输出进入文本任务目录。
2. **翻译**：保存本次选定范围的译文、真实 API 返回、校验和断点记录；不在这一步生成可玩副本。
3. **嵌入游戏内**：核对本次结果和原游戏来源，将资源包、字体或启动适配写入独立可玩副本；不修改原游戏或原存档。

必须明确区分提取支持、翻译支持和可玩部署支持。不能因页面存在第三步，或已经发布独立译文，
就把尚未验证的引擎版本显示为可以嵌入。来源缺失、译文不完整、版本不符、补丁覆盖或编码未知时应明确停止。
不自动重译旧任务、不绕过费用确认、不把重启恢复变成新的付费调用。

人物译名和开场范围继续遵循
[人物译名规则](character-glossary.md)与[开场选取规则](opening-selection.md)，本规则不替代这些校验。

## 4. 启动入口、重建和失败处理

- `full` 使用 `translation-formal` 和 `启动正式版.cmd`；`partial` 使用 `translation-test` 和 `启动测试版.cmd`。
  旧 `pilot` 仅兼容映射到测试版，不新增第三种可玩目录。
- 游戏级目录不生成含义不明确的通用 `启动汉化版.cmd`；这个入口只能位于具体版本内部。
- 测试版与正式版入口使用相对路径，分别指向对应版本；重建其中一个不能改动另一个。
- `.deploy-编号.partial` 只能是公共发布流程创建的临时同级目录，不是新的正式输出类型。
- 校验全部通过后再发布；已有同类版本及存档由 `publish_playable()` 归档到 `.history`，不直接删除或覆盖。
- 发布失败时保留可诊断的失败状态，并按公共逻辑回滚已有版本；不返回“部署完成”或可用入口。
- 只覆盖已经确认由 Nagi 管理的启动入口，不覆盖用户自建文件。

## 5. 开发验证和维护资料

**验证脚本也必须遵守目录约定，不能用“只是测试”为理由另建引擎专用顶层目录。**

- 自动测试使用 `pytest` 的 `tmp_path`；其他开发验证使用系统临时目录。
  在临时根目录中创建 `translations`，由同一公共流程推导同级 `playable`，仍保留引擎族、游戏、任务和测试/正式层级。
- 不把测试输出指向用户现有的测试版或正式版，不为隔离测试而改写公共工作流算出的路径或布局版本。
- 实机验证只操作独立副本。使用离线测试文字时，报告必须说明它不是实际 API 翻译，也不代表全文或全路线验证。
- 验证结束后清理本次生成的游戏副本和一次性脚本，避免遗留可再次生成错误目录的工具。
- 需要保留的截图、验证报告和维护备份统一进入 `state_root() / "maintenance" / 日期与任务标识`。
  状态目录由公共接口决定；已有 `.pico` 数据继续按兼容规则读取，不手工另建平行 `.nagi` 状态树。
- 清理或移动前核对最终绝对路径及内容归属，只处理本任务生成的资料；不得清理原游戏、用户存档或无关任务。
- 私人截图、游戏资源、译文、API 返回、密钥和维护备份不进入源码发行包。

禁止的新增方式包括工作目录顶层的 `qlie-verification/`、`新引擎-verification/`、
`新引擎-deployments/`、`新引擎-experiments/`，以及为新引擎复制一套独立的目录或启动器生成逻辑。

## 6. 新引擎接入验收清单

- [ ] 显式识别并注册引擎族，版本和适配范围保存在元数据中；未知引擎不会误走其他适配器。
- [ ] 提取、翻译、部署和恢复均经过公共工作流，输出不进入原游戏或源码仓库。
- [ ] 通过完整部署入口验证部分/全文两种模式，而不只测试底层回包函数。
- [ ] 文本任务进入 `translations/引擎族/游戏/任务`，可玩结果进入相应的固定测试/正式位置。
- [ ] 游戏级启动入口、版本内部组件和相对路径均正确，没有额外顶层目录或 `localized-game-*` 嵌套。
- [ ] 两种模式互不覆盖；同类重建保留旧版及存档，失败不会发布半成品。
- [ ] 同名游戏的不同安装、不同任务之间保持隔离；自定义文本根目录时仍得到正确的同级 `playable`。
- [ ] 原游戏、原存档保持不变；任务恢复不会自动调用模型或扩大翻译范围。
- [ ] 新增测试使用临时目录和合成数据；实机验证资料进入内部维护目录，一次性副本和脚本完成清理。
- [ ] 在 README“功能边界”表对应引擎行填写可核查的游戏示例，并在表后补充示例来源。
- [ ] 更新支持范围说明、使用文档及 `release/source-files.txt`，不将私人验证资料打包发布。

目录与入口回归参考：`tests/test_translation_storage.py`、`tests/test_playable_layout.py`、
`tests/test_game_launcher.py`、`tests/test_translation_workflow.py`、`tests/test_qlie_deployment.py`、`tests/test_game_deployment.py`。
新引擎应扩展相同契约的测试，不以引擎专用目录作为测试通过条件。

用户侧目录说明见[翻译资料与本机启动依赖](../translation-storage.md)。
